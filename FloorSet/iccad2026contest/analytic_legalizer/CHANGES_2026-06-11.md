## 1. What the architecture does (as-found)

Pipeline (`optimizer.py:MyOptimizer.solve`), unchanged by this pass:

```
parse_and_init → prepack_clusters → analytic_place → skyline_legalize
                                                          │
   _local_slide_refine ← enforce_hard ← slide_boundary ←─┘
```

The whole legalize→slide→enforce chain is run once per
*(seed × wirelength-model × skyline-config)* combination, and the candidate that
minimizes the proxy `area · HPWL · exp(3·soft/n)` is kept. The analytic placer
(`quadratic_placer.py`) is only a *guide*; `skyline_legalizer.py` does the real
constructive strip-packing. This is a sound "analytic guide → legalize → select"
design and it is **100% feasible** across all 100 cases.

## 2. The issue I found (root cause)

**The expensive multi-config search was gated to `block_count >= 116`.** Every case
below 116 blocks got only `1 WL model × 2 skyline configs = 2 legalizations`, while
n≥116 got `2 WL models × 8 configs = 16`.

That gate was correct under the **old** scoring weight `e^n`, where case n=120 alone
is ~63% of the grade and everything below n=116 is ~1% combined — so spending search
budget there was pointless.

But the evaluator's weighting was changed to **`e^(n/12)`** (see the local diff in
`iccad2026_evaluate.py:compute_total_score`). Under `e^(n/12)`:

- n=120 is ~34% (not 63%); **cases below n=111 are ~28% combined** (not ~1%).
- Those under-searched small/mid cases were empirically the **worst-scoring** ones:
  costs of **2.0–3.3** versus 1.57–1.84 for the big cases (e.g. n=22 → 3.29,
  n=35 → 3.03, n=29 → 2.86).
- Small cases are *cheap* to legalize, so the rich search there is nearly free.

So the architecture was still tuned for the retired "only n≥116 matters" regime while
being graded on a weighting where half the score lives elsewhere — and precisely in
the cases it was under-optimizing.

## 3. The change

`optimizer.py`: lowered the rich-search gate so **every block count gets the full
search** (`2 WL models × 8 skyline configs`):

```python
RICH_SEARCH = block_count >= 1   # was: block_count >= 116
WL_MODELS = ("quadratic", "lse") if RICH_SEARCH else ("quadratic",)
```

This is **safe by construction**: the old small-case config set
`{(0.20,…), (0.45,…)}` is a strict *subset* of the rich set, and candidate selection
keeps the min-proxy layout — so the search space only grows and the proxy-selected
result can never get worse. The aggregate improvement (1.9157 → 1.8668) and the
per-case spot-checks (idx0 n=21: 2.46→1.95; idx50 n=71: 1.97→1.74; idx99 n=120:
unchanged) confirm the gains land on exactly the small/mid cases as predicted.

**Cost:** full-run wall-clock went to ~4m18s for all 100 cases (~2.6 s/case). The
official runtime factor is `max(0.7, R^0.3)` (weak, floored) and is computed
*per-case* against the cross-submission median; sub-3s legalizations are not a
practical risk. Locally the harness uses a neutral `RuntimeFactor = 1.0`.

## 4. One experiment that did *not* pan out (reverted)

I tried adding two **HPWL-aware width-selection** configs (`hpwl_weight=0.5`,
`refine_widths=True`) on the theory that the skyline width search ignores HPWL
(`hpwl_weight=0` everywhere) even though HPWL is the dominant cost gap. On the
dominant cases (95–99) the score was **identical** (1.6908) — the proxy never
selected those candidates — so they only added runtime. **Reverted.** Noted here so
the idea isn't re-tried blindly: moving HPWL needs a structural change (below), not a
width-selection tweak.

## 6. Where the score still bleeds (next levers, biggest first)

These are unchanged by this pass and remain the path to a bigger win. They line up
with `ALGORITHM_REPORT_AND_UPGRADE_ANALYSIS.md`:

1. **HPWL gap (0.45–1.94)** is the single largest cost term and the skyline packer
   only respects it weakly (via `λ·|x−cx|`). The real fix is a **warm-started
   fixed-outline local search** (sequence-pair / B*-tree SA) *seeded from the skyline
   result*, minimizing the true objective. Earlier "Bstar bad" was almost certainly
   cold-start SA; warm-starting from the dense feasible layout is the difference.
2. **Boundary violations (363 total)** drive `exp(2·V_rel)` and hurt small cases most
   (each miss is a larger fraction of `N_soft`). A frontier-set boundary-repair pass
   (pull the whole touching set flush, not the current single-block clip-slide) or
   folding boundary into the search objective would help.
3. **Area gap (0.23–0.85)**: replace the discrete aspect ladder with a 1-D width
   search and replace the greedy gap-fillers with constraint-graph compaction.
4. **Soft-block aspect ratio is a free DOF that is never used** — soft blocks are
   locked to squares (`w=h=√area` in `parse_and_init`). Letting the legalizer choose
   shapes could cut both area and HPWL (but must preserve the 1% area tolerance and
   overlap-freeness).

> Note on the selection proxy: the optimizer ranks candidates by
> `area · HPWL · exp(3·soft/n)`, a *multiplicative* surrogate, whereas the true
> quality term is *additive* (`1 + 0.5·(HPWL_gap + Area_gap)`). Baselines aren't known
> at solve time so an exact match isn't possible, but this mismatch can mis-rank
> candidates where one term is large — worth revisiting alongside lever #1.
